Техническое задание
Утилита генерации синтетического спроса по корреспонденциям

1. Назначение

Разработать отдельную консольную утилиту на Python, предназначенную для подготовки недостающих входных данных для проекта timetable-transit-assigment.

Утилита не является частью основного вычислительного конвейера проекта и не должна встраиваться в основной C++-бинарник. Ее назначение - автономная генерация синтетических данных о спросе по корреспонденциям между районами и разбиении этого спроса по временным интервалам.

Утилита должна использовать существующий файл:

D:\Development\projects\timetable-transit-assigment\data\test\connection_segments_input.csv

как источник структурной информации о сети, но не как источник истинного спроса.


2. Что должно быть сгенерировано

Утилита должна формировать следующие данные:

1. Список временных интервалов одинаковой продолжительности.
2. Спрос по корреспонденциям для каждой пары районов отправления и назначения.
3. Разбиение спроса по этим временным интервалам.

Результат должен быть пригоден для последующей загрузки в основной проект без концептуального противоречия с доменной моделью:

- TimeInterval
- DemandEntry


3. Архитектурные требования

1. Утилита должна быть отдельной программой, физически отделенной от основного проекта.
2. Утилита должна быть консольной.
3. Реализация должна быть выполнена на Python.
4. Код должен быть чистым, детерминированным и максимально декларативным.
5. Следует предпочитать чистые функции, неизменяемые структуры данных и явное разделение стадий вычислительного конвейера.
6. Логика генерации должна быть воспроизводимой через явно задаваемое начальное значение генератора.
7. Производительность не является приоритетом, но утилита должна корректно работать на полном тестовом файле проекта.


4. Источник данных и роль входного файла

Файл connection_segments_input.csv должен использоваться только для извлечения структуры транспортной сети, в частности:

1. множества идентификаторов зон;
2. факта присутствия связей зона-остановка, остановка-зона, остановка-остановка;
3. временного диапазона расписания;
4. при необходимости - вспомогательных структур для оценки "массы" зоны или грубой транспортной связанности.

Важное ограничение:

Утилита не должна интерпретировать connection_segments_input.csv как наблюдаемый спрос. Этот файл описывает транспортное предложение, а не пассажирские потоки. Поэтому значения спроса должны синтезироваться отдельной моделью.


5. Требования к входным данным

5.1. Основной вход

CSV-файл connection_segments_input.csv содержит как минимум следующие поля:

- FROM_STOP_ID
- TO_STOP_ID
- TIME
- LENGTH
- FROM_ZONE_ID
- TO_ZONE_ID
- FARE
- TRIP_ID
- LINE_ID
- FROM_INDEX
- DEP
- TO_INDEX
- ARR

5.2. Семантика использования полей

1. FROM_ZONE_ID и TO_ZONE_ID используются для извлечения множества районов.
2. DEP и ARR используются для оценки фактического временного диапазона движения.
3. Поля рейсов и сегментов могут использоваться только как вспомогательная информация при вычислении синтетических признаков зон.
4. Значения -1 должны трактоваться как отсутствие соответствующего объекта.


6. Требования к выходным данным

Утилита должна формировать два независимых CSV-файла.

6.1. Файл временных интервалов

Имя по умолчанию:

time_intervals.csv

Формат:

interval_id,start_sec,end_sec
1,21600,25200
2,25200,28800
...

Требования:

1. Интервалы должны иметь одинаковую продолжительность.
2. Интервалы не должны пересекаться.
3. Интервалы должны полностью покрывать выбранный период моделирования.
4. Представление времени - в секундах от начала суток.

6.2. Файл спроса по корреспонденциям

Имя по умолчанию:

od_demand.csv

Формат:

origin_zone_id,destination_zone_id,interval_id,passengers
1,2,1,3.5
1,2,2,4.1
...

Требования:

1. Каждая строка описывает спрос для одной пары районов и одного временного интервала.
2. Значение passengers должно быть неотрицательным вещественным числом.
3. Для пар вида origin_zone_id = destination_zone_id строки по умолчанию не формируются, если явно не включен режим генерации внутрайонных перемещений.
4. Для отсутствующего спроса строка может либо отсутствовать, либо присутствовать со значением 0. Предпочтительный вариант - не писать нулевые строки, если это не мешает последующей загрузке.


7. Модель генерации данных

7.1. Общий принцип

Генерируемый спрос должен быть синтетическим, но структурно правдоподобным. Он должен зависеть от множества районов и, по возможности, от грубых характеристик сети, извлеченных из входного файла.

7.2. Этап 1. Извлечение множества районов

Утилита должна построить множество районов как объединение:

- всех корректных FROM_ZONE_ID;
- всех корректных TO_ZONE_ID.

Результирующее множество районов должно быть отсортировано по возрастанию идентификатора.

7.3. Этап 2. Построение временного диапазона

Утилита должна уметь работать в двух режимах:

1. Явно заданный диапазон времени через аргументы командной строки.
2. Автоматическое определение диапазона на основе DEP и ARR из входного файла.

Предпочтительный режим по умолчанию для тестового набора:

- начало периода: 21600 секунд (06:00:00)
- конец периода: 82800 секунд (23:00:00)

Это согласуется с текущими параметрами проекта.

7.4. Этап 3. Построение временных интервалов

Утилита должна разбивать выбранный период на интервалы одинаковой длины.

Значение по умолчанию:

- длина интервала: 3600 секунд

То есть при диапазоне 06:00-23:00 формируется 17 интервалов.

7.5. Этап 4. Оценка "массы" района

Для каждого района должна быть вычислена синтетическая характеристика массы района. Допустимые источники:

1. количество инцидентных сегментов зона-остановка и остановка-зона;
2. число уникальных остановок, связанных с районом;
3. число всех сегментов, в которых район фигурирует как точка входа или выхода.

Требование:

Даже если район имеет малую наблюдаемую представленность в файле, его масса не должна обращаться в ноль. Следует использовать регуляризацию, например:

zoneMass = baseMass + derivedMass

где baseMass > 0.

7.6. Этап 5. Генерация агрегированного суточного спроса по OD

Для каждой пары различных районов (i, j) необходимо вычислить syntheticDailyDemand(i, j).

Теоретически корректная базовая модель:

dailyDemand(i, j) = scale * attraction(i) * attraction(j) * decay(i, j) * noise(i, j)

где:

- attraction(i) >= 0 - функция от массы района i;
- decay(i, j) in (0, 1] - штраф за удаленность или слабую связанность;
- noise(i, j) > 0 - небольшой детерминированный шум;
- scale > 0 - глобальный масштаб.

Минимально допустимая реализация:

1. attraction(i) = sqrt(zoneMass(i))
2. decay(i, j) = 1.0
3. noise(i, j) - псевдослучайный множитель из узкого диапазона, например [0.9; 1.1], детерминированный через начальное значение генератора и пару (i, j)

Предпочтительная улучшенная реализация:

1. использовать грубую меру связности между районами;
2. если ее нет, использовать хотя бы ослабление спроса для слабосвязанных пар;
3. обеспечить асимметрию спроса, чтобы (i, j) и (j, i) не были обязаны совпадать.

7.7. Этап 6. Временной профиль спроса

Суточный спрос каждой OD-пары должен распределяться по временным интервалам по одному и тому же базовому профилю времени суток.

Требования к профилю:

1. все веса неотрицательны;
2. сумма весов по всем интервалам равна 1;
3. профиль должен быть реалистичным, а не равномерным.

Рекомендуемый профиль:

- слабый спрос ранним утром;
- утренний пик;
- дневное плато;
- вечерний пик;
- спад поздно вечером.

Допускается:

1. фиксированный табличный профиль;
2. параметризованный профиль как сумма двух "горбов" (утреннего и вечернего);
3. небольшая OD-специфическая детерминированная вариация вокруг базового профиля.

7.8. Этап 7. Разложение суточного спроса по интервалам

Для каждой OD-пары и каждого интервала:

intervalDemand(i, j, a) = dailyDemand(i, j) * temporalShare(i, j, a)

После вычисления должна обеспечиваться численная корректность:

1. все значения конечны;
2. все значения неотрицательны;
3. сумма по интервалам должна совпадать с dailyDemand(i, j) с учетом допустимой численной погрешности.


8. Детерминизм и воспроизводимость

1. Утилита должна принимать начальное значение генератора через интерфейс командной строки.
2. При одинаковых входных данных и одинаковом начальном значении генератора результаты должны быть идентичны.
3. Генерация не должна зависеть от порядка обхода хеш-коллекций.
4. Все списки в выходных файлах должны быть стабильно отсортированы:
   - интервалы по interval_id;
   - спрос по origin_zone_id, затем destination_zone_id, затем interval_id.


9. Требования к интерфейсу командной строки

Утилита должна поддерживать как минимум следующие аргументы:

1. --input <path>
   путь к connection_segments_input.csv

2. --output-dir <path>
   директория для выходных файлов

3. --start-sec <int>
   начало периода моделирования в секундах от начала суток

4. --end-sec <int>
   конец периода моделирования в секундах от начала суток

5. --interval-sec <int>
   длина временного интервала в секундах

6. --seed <int>
   начальное значение генератора

7. --demand-scale <float>
   глобальный масштаб синтетического спроса

8. --include-intrazonal <true|false>
   генерировать ли спрос внутри одного района

9. --sparse-od-threshold <float>
   нижний порог, ниже которого спрос можно не записывать в файл

10. --auto-time-range <true|false>
    использовать ли автоматическое определение временного диапазона по входному файлу

11. --verbose
    вывод диагностической информации в консоль


10. Валидация и диагностика

Утилита должна выполнять базовую валидацию:

1. входной файл существует и читается;
2. обязательные столбцы присутствуют;
3. start_sec < end_sec;
4. interval_sec > 0;
5. длина периода кратна длине интервала;
6. начальное значение генератора корректно;
7. выходной каталог может быть создан или уже существует.

Утилита должна печатать краткую диагностическую сводку, как минимум:

- число считанных строк входного файла;
- число найденных районов;
- диапазон фактических DEP/ARR;
- число интервалов;
- число OD-пар;
- суммарный сгенерированный спрос;
- число записанных строк od_demand.csv.


11. Требования к качеству модели

Сгенерированные данные не обязаны быть калиброваны по реальному городу, но должны удовлетворять следующим принципам:

1. спрос не должен быть полностью равномерным;
2. спрос должен зависеть от структуры зон;
3. временной профиль должен быть правдоподобным;
4. должны существовать как сильные, так и слабые OD-пары;
5. модель должна быть прозрачной и параметризуемой;
6. формулы должны быть простыми для дальнейшей замены на более содержательную модель.

13.8. Что вызывает сомнения или требует осторожной интерпретации

1. Все значения FARE во входном транспортном предложении равны нулю. Это согласуется с текущей договоренностью, что 0 означает бесплатный проезд, но тарифная часть обобщенного сопротивления фактически не участвует в выборе. Поэтому этот прогон проверяет временные и пересадочные компоненты лучше, чем тарифную чувствительность.
2. Спрос синтетический и не калиброван по наблюдаемым пассажирским данным. Его нельзя интерпретировать как реальную матрицу корреспонденций.
3. В connections.csv осталось много выбранных соединений с нулевым assigned_passengers. Это не ломает расчет, потому что баланс массы при распределении спроса корректен, но увеличивает размер отчетности. Для презентационного вывода может быть полезен дополнительный отфильтрованный отчет, не меняющий математический результат.
4. В shares.csv есть 373 строки с очень малыми положительными вероятностями ниже 1e-12. Это ожидаемый численный хвост MNL/Box-Cox распределения спроса; он не нарушает балансы, но требует аккуратного округления в пользовательских отчетах.
5. Структурная достижимость отсекла только 1360 ветвей, то есть сама по себе она остается слабым фильтром на этом наборе. Основной контроль размера поиска обеспечило отсечение по нижним оценкам. Это не эвристика, но показывает, что производительность на более крупных сценариях будет зависеть прежде всего от качества нижних оценок и локальных для задачи допусков.
6. В loads.csv для уровней линии, маршрута и рейса поле passengers пустое, а агрегированная метрика записана в passenger_segments. Для уровня сегмента, наоборот, passengers заполнено, а passenger_segments пустое. Это математически объяснимо различием уровней агрегации, но формат может быть неочевиден внешнему читателю; при финализации отчетного формата стоит либо явно документировать это правило, либо унифицировать имена колонок.
7. В skim_matrix.csv число transfers может быть дробным при усреднении, потому что это агрегированный skim-атрибут, а не число пересадок одного конкретного соединения.
8. В assignment_summary.txt примеры соединений могут показывать assigned=0.000 из-за округления или нулевого назначения после распределения спроса. Это корректно, но для демонстрационного отчета может выглядеть странно без пояснения.

13.9. Итоговая оценка прогона

Прогон можно считать корректным демонстрационным расчетом на синтетическом спросе. Входные файлы спроса валидны, основной расчет завершился без ошибок, все OD-временные задачи получили найденные соединения, распределение сохранило спрос, а загрузки были построены на требуемых уровнях детализации.

С теоретической точки зрения результаты согласуются с текущей реализацией назначения пассажирского спроса по расписанию:

1. запись спроса задает OD-временную задачу;
2. поиск строит допустимое множество соединений по расписанию;
3. отбор оставляет допустимые альтернативы, локальные для задачи;
4. распределение спроса назначает спрос по альтернативам;
5. выходной слой агрегирует назначенный спрос в соединения, доли, сегменты пути и загрузки.

Основные ограничения данного прогона относятся не к корректности алгоритма, а к интерпретации:

1. спрос является синтетическим;
2. тарифный компонент не проверяется содержательно, так как все значения FARE нулевые;
3. часть отчетных таблиц содержит математически корректные, но презентационно шумные строки;
4. формат loads.csv требует явного пояснения различия между passengers и passenger_segments;
5. формат skim_matrix.csv требует пояснения, что его атрибуты являются агрегированными значениями по выбранному подмножеству соединений.
