
Работа близка к завершенной базовой реализации алгоритма.

Реализован основной расчетный контур:
1. загрузка подготовленного транспортного предложения;
2. загрузка спроса по OD-парам и временным интервалам;
3. построение допустимых соединений по расписанию;
4. отбор релевантных альтернатив;
5. распределение спроса между выбранными альтернативами;
6. расчет загрузок на уровнях сегмента, рейса, маршрута и линии;
7. выгрузка результатов в таблицы и сводку;
8. автономная утилита генерации синтетического спроса.

Доменное построение сегментов из сырой модели уже есть в коде, но как режим запуска сейчас поддержан только вход с уже подготовленными сегментами соединений.


Текущий поддерживаемый режим запуска принимает каталог с готовыми сегментами транспортного предложения и файлами спроса.

Обязательные файлы:
1. connection_segments_input.csv;
2. time_intervals.csv;
3. od_demand.csv.

Файл params.txt игнорируется.

Принято, что:
1. connection_segments_input.csv содержит уже подготовленные сегменты транспортного предложения;
2. сегменты с расписанием имеют времена отправления/прибытия и валидные идентификаторы линии, маршрута и рейса;
3. пешеходные сегменты имеют TRIP_ID = -1;
4. значение -1 в полях DEP, ARR, TRIP_ID, ROUTE_ID, LINE_ID, FROM_ZONE_ID, TO_ZONE_ID трактуется как отсутствие значения;
5. FARE = 0 трактуется как бесплатный проезд;
6. черезполуночные поездки не должны попадать в расчет;
7. FROM_INDEX и TO_INDEX являются вспомогательными индексами внутри рейса и не являются необходимыми для алгоритма.

3. Реализовано:

3.1. Модель соединения

Соединение представляется как последовательность элементов пути: ходьба, поездка, ожидание или пересадка. Метрики соединения являются производными от этой последовательности.

Важно, что одно и то же физическое соединение не должно иметь противоречивые значения времени, числа пересадок, стоимости или обобщенного сопротивления. Все эти величины вычисляются из трассы соединения и параметров модели.

3.2. Задача поиска

Единицей поиска является OD-временная задача:

район отправления, район назначения, временной интервал.
Поиск строит множество допустимых альтернатив только для этой задачи.

3.3. Поиск соединений

Реализован поиск по расписанию методом ветвей и границ.

В поиске учитываются:
1. допустимое окно первой посадки;
2. времена отправления и прибытия рейсов;
3. минимальное и максимальное ожидание пересадки;
4. максимальное число пересадок;
5. запрет циклов и некорректных повторных посадок;
6. доминирование частичных ветвей;
7. допуски по времени, пересадкам и обобщенному сопротивлению.

Результат поиска - допустимое множество альтернатив для соответствующей OD-временной задачи.

3.4. Отбор альтернатив

После поиска выполняется дополнительный отбор полных соединений. Он устраняет доминируемые альтернативы и применяет допуски на уровне полного соединения.

3.5. Распределение спроса

Спрос распределяется между выбранными альтернативами по модели дискретного выбора.

Учитываются:
1. время в транспорте;
2. вход к первой посадке;
3. выход после последней поездки;
4. ходьба при пересадке;
5. ожидание пересадки;
6. число пересадок;
7. стоимость проезда;
8. временная полезность относительно интервала спроса;
9. коэффициент независимости для похожих альтернатив.

3.6. Загрузки

После распределения спроса назначенный поток агрегируется в загрузки:
1. по сегментам соединений;
2. по рейсам;
3. по маршрутам;
4. по линиям.

Загрузка считается для сегмента вида "сел на i, вышел на j". Раскладка этого сегмента на соседние перегоны i -> i+1 -> ... -> j сейчас не выполняется.


4. Некоторые уточнения, которые статья не формализует явно:

1) Каноническая модель соединения.
   Соединение хранит трассу, а метрики являются функциями трассы.

2) Локальность по OD-временной задаче.
   Поиск, доминирование, допуски, отбор и распределение спроса работают в рамках одной математической задачи, а не в общей группе по району отправления.

3) Компонентное обобщенное сопротивление.
   Вместо одной агрегированной формулы проект хранит и использует разложение по смысловым компонентам времени, пересадок и стоимости.

4) Отсечение по остаточным нижним оценкам.
   Для частичной ветви строятся допустимые нижние оценки продолжения. Ветвь отсекается только если доказано, что любое ее продолжение уже не сможет попасть в допустимое множество.


5. Параметры расчетной модели
   В проекте уже существует модель параметров расчета. В поддерживаемом pair-file режиме расчет использует встроенные значения по умолчанию, а params.txt пока не подключает пользовательские значения.

Основные группы параметров:

1) Ограничения пересадок:
   - максимальное число пересадок;
   - минимальное ожидание пересадки;
   - максимальное ожидание пересадки;
   - разрешение стартового и финального ожидания.

2) Веса обобщенного сопротивления при поиске:
   - время в транспорте;
   - вход к первой посадке;
   - выход после последней поездки;
   - ходьба при пересадке;
   - ожидание пересадки;
   - число пересадок;
   - стоимость проезда;
   - нормализация стоимости проезда.

3) Допуски на этапе поиска:
   - множитель и добавка по обобщенному сопротивлению;
   - множитель и добавка по времени поездки;
   - множитель и добавка по числу пересадок.

4) Допуски на этапе отбора альтернатив:
   - аналогичные допуски по обобщенному сопротивлению, времени поездки и числу пересадок, но применяемые уже к полным соединениям.

5) Параметры распределения спроса:
   - вес воспринимаемого времени поездки;
   - вес временной полезности;
   - вес стоимости проезда;
   - веса компонент воспринимаемого времени поездки;
   - штрафы за раннее и позднее отправление относительно интервала спроса;
   - параметр чувствительности модели выбора;
   - параметр Box-Cox преобразования;
   - параметры коэффициента независимости похожих альтернатив.

6) Параметры предварительной обработки:
   - способ оценки пешеходной стоимости;
   - параметры скорости/временной агрегации;
   - строгость обработки рейсов и остановочных времен;
   - политика черезполуночных поездок;
   - дедупликация пешеходных сегментов.

Эта группа относится к доменному контуру построения сегментов из сырой модели входа. При входе с уже подготовленными сегментами она не меняет сами сегменты транспортного предложения.

Парсер params.txt также реализован. Он умеет читать структуру параметров и отображать ее в доменную модель параметров расчета.

6. Утилита генерации синтетического спроса

В проекте реализована отдельная Python-утилита tools/demand_generator для генерации недостающих входных файлов:
1. time_intervals.csv;
2. od_demand.csv.

7. Проверочные прогоны

Выполнялись проверочные расчеты на сгенерированном спросе.

По малому проверочному входу:
1) расчет завершается без критических ошибок;
2) общий спрос совпадает с назначенным спросом в пределах численной погрешности;
3) вероятности по OD-временным задачам суммируются к 1;
4) загрузки формируются на требуемых уровнях;
5) отсечение по нижним оценкам существенно уменьшает объем поиска без изменения найденного результата.

По сценарию с 75 OD-парами и 4 интервалами:
1) было сформировано 300 OD-временных задач;
2) все задачи получили непустое множество альтернатив;
3) суммарный спрос был полностью назначен;
4) отрицательных или неконечных пассажиропотоков в таблицах не обнаружено;
5) загрузки линий, маршрутов, рейсов и сегментов согласованы по суммарной массе passenger_segments.

По логу timetable-20260429-033459.log этот прогон проходил так:
1) загружен вход в формате готовых CSV-файлов из data/test: connection_segments_input.csv, time_intervals.csv, od_demand.csv;
2) params.txt найден, но намеренно проигнорирован;
3) из входа построено 69321 сегмент маршрута и 1709347 сегментов соединения, из них 26734 пешеходных и 1682613 с расписанием;
4) загружено 4 временных интервала и 300 записей спроса;
5) построены индексы транспортного предложения;
6) поиск выполнен по 300 OD-временным задачам, сгруппированным в 60 пакетов;
7) найдено 81318 соединений, после отбора осталось 81261;
8) распределение спроса сформировало 29083 значимые доли, еще 52235 численно незначимых долей были подавлены;
9) общий спрос составил 29038.043 пассажира и полностью совпал с назначенным спросом в сводке;
10) расчет занял 121.270 секунды;
11) сформированы выходные таблицы: od_summary.csv, connections.csv, shares.csv, segments.csv, loads.csv и assignment_output.json.

Единственное предупреждение в этом прогоне связано с тарифом: вес стоимости проезда положителен, но во входных сегментах нет положительных значений FARE, поэтому тарифный компонент в этом сценарии фактически равен нулю.


8. Вызывает сомнения:

8.1. Стоимость проезда
Модель стоимости проезда реализована, но текущий тестовый вход имеет FARE = 0 для всех сегментов. Поэтому тарифный компонент присутствует, но практически не проверен на данных с положительной стоимостью.

8.2. Параметры
params.txt пока не подключен.
Парсер params.txt и модель параметров уже реализованы.

8.3. Пользовательский вход для исходного расписания
Статья начинает с исходных маршрутов, рейсов и пешеходных связей.
В коде уже есть слой, который строит сегменты маршрутов и сегменты соединений из сырой модели входа.
Но этот путь не оформлен как поддерживаемый режим запуска.

8.4. Ограничение вместимости
Проект рассчитывает загрузки после распределения спроса, но не изменяет выбор пассажиров из-за перегрузки.
