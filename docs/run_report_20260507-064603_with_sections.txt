3. Режимы учета спроса, временных интервалов и построения деревьев
------------------------------------------------------------------

В программе реализовано несколько расчетных сценариев. Они используют одни и
те же входные файлы, но отвечают на разные вопросы.

Режим задается блоком searchExecution в params.txt.

3.1 Общезональный поиск путей на сутки
--------------------------------------
Это режим текущего прогона.

Его явная конфигурация:

    'searchExecution': {
        'mode': 'origin_period',
        'originScope': 'declared_zones',
        'timeDomainSource': 'service_day',
        'destinationScope': 'declared_zones',
        'resultProjection': 'completion_targets',
        'partialRetentionScope': 'tree_global'
    }

Если блок searchExecution отсутствует, сейчас используется именно эта
конфигурация по умолчанию.

Смысл режима:
    исходные районы берутся из полного списка объявленных районов;
    целевые районы также берутся из полного списка объявленных районов;
    для каждого исходного района строится одно дерево;
    временной горизонт дерева - полные сутки;
    результат сохраняется по целевым районам, а не по строкам спроса.

Для данной модели это означает:
    227 районов -> 227 деревьев;
    каждое дерево -> ко всем 227 районам;
    всего рассматривается 227 * 227 = 51 529 пар районов.

В этом режиме od_demand.csv и time_intervals.csv не
задают область поиска. Они не определяют число деревьев, целевые районы,
временные окна и объемы пассажиров. Поэтому этот режим является поиском
альтернатив, а не расчетом распределения спроса.

Ситуация с пассажиром, ожидающим автобус в 08:00, а первый подходящий автобус
приходит в 10:00, в этом режиме не приводит к потере пути только из-за
интервала спроса: дерево строится на сутки, поэтому отправление в 10:00
попадает в область поиска. Путь может быть отброшен только по другим правилам:
например, по недостижимости, ограничению пересадок, доминированию или
финальным допускам качества.

3.2 Назначение спроса по OD-задачам и временным интервалам
----------------------------------------------------------
Этот режим включается так:

    'searchExecution': {
        'mode': 'interval_local'
    }

Смысл режима:
    od_demand.csv задает активные корреспонденции между районами и объемы
    пассажирского спроса;

    time_intervals.csv задает временные интервалы, к которым относятся строки
    спроса;

    для каждой положительной строки спроса формируется задача вида
    "исходный район - целевой район - временной интервал";

    найденные альтернативы проходят отбор;

    затем пассажирский спрос распределяется между выбранными альтернативами;

    после распределения спроса могут рассчитываться загрузки сегментов,
    элементов рейсов, рейсов, маршрутов и линий.

Этот режим меняет условия задачи:

    поиск идет не по всем 227 * 227 парам районов, а только по активным строкам
    спроса;

    число деревьев или расчетных пакетов в общем случае не равно 227;

    целевые районы берутся не из полного списка районов, а из положительных
    OD-записей;

    временные интервалы из time_intervals.csv задают окна первой посадки.

Именно в этом режиме возможна ситуация: пассажир относится к интервалу 08:00,
а первый подходящий автобус отправляется только в 10:00 и не попадает во
временное окно поиска. Тогда путь с отправлением в 10:00 не будет найден для
этой строки спроса. Если других допустимых альтернатив нет, соответствующий
спрос не получит пути и не будет распределен.

Временной интервал спроса трактуется как ограничение на область поиска. 
Такой режим подходит для интервального назначения спроса.

3.3 Деревья по исходным районам с результатом по строкам спроса
---------------------------------------------------------------

Есть промежуточный вариант: строить деревья по исходным районам, но сохранять
результат только для задач спроса.

Типовая конфигурация:

    'searchExecution': {
        'mode': 'origin_period',
        'originScope': 'active_demand_origins',
        'timeDomainSource': 'demand_induced',
        'destinationScope': 'demand_destinations',
        'resultProjection': 'demand_tasks',
        'partialRetentionScope': 'projection_slot_local'
    }

Смысл режима:
    исходные районы берутся из положительного спроса;
    целевые районы берутся из положительного спроса;
    временные области строятся по интервалам спроса;
    результат сохраняется по строкам спроса;
    после поиска может выполняться распределение пассажиров и расчет загрузок.

Число деревьев в этом режиме в общем случае равно не числу всех районов, а
числу исходных районов, встречающихся в положительном спросе. Если спрос есть
не из всех 227 районов, деревьев будет меньше 227.

Для ситуации "пассажир в 08:00, автобус в 10:00" результат зависит от
timeDomainSource:
    если timeDomainSource = 'demand_induced', временная область строится из
    интервалов спроса. Если интервал не покрывает 10:00, путь с первой посадкой
    в 10:00 не попадет в поиск;

    если timeDomainSource = 'service_day', дерево строится на сутки, и путь с
    первой посадкой в 10:00 может быть найден, но затем он еще может быть
    удален правилами допустимости относительно интервала спроса, если такие
    правила включены параметрами отбора.

3.4 Суточные деревья по всем районам, но результат только по спросу
-------------------------------------------------------------------
Еще один возможный вариант:
    'searchExecution': {
        'mode': 'origin_period',
        'originScope': 'declared_zones',
        'timeDomainSource': 'service_day',
        'destinationScope': 'declared_zones',
        'resultProjection': 'demand_tasks',
        'partialRetentionScope': 'projection_slot_local'
    }

Смысл режима:
    деревья строятся по всем объявленным районам;
    временной горизонт каждого дерева - сутки;
    достижение разрешено до всех объявленных районов;
    но результат сохраняется только для OD-задач из спроса.

В этом режиме число деревьев равно числу районов, потому что
originScope = 'declared_zones'. Однако итоговые пути считаются не для всех
51 529 пар районов, а только для строк спроса. Поэтому этот режим не является
полным общезональным поиском, хотя и строит 227 суточных деревьев.

Ситуация с отправлением в 10:00 здесь отличается от строгого интервального
режима: само дерево находит пути по всему дню. Но если параметры отбора
запрещают соединения, слишком далеко выходящие за интервал спроса, путь все
равно может быть удален после поиска.

3.5 Режим с периодом назначения вместо полных суток
---------------------------------------------------
Поле timeDomainSource может принимать значение:
    'assignment_period'

В этом случае временная область строится не как полные сутки, а по интервалам
из time_intervals.csv, расширенным на preAssignPeriod и postAssignPeriod.

Пример:
    'searchExecution': {
        'mode': 'origin_period',
        'originScope': 'declared_zones',
        'timeDomainSource': 'assignment_period',
        'destinationScope': 'declared_zones',
        'resultProjection': 'demand_tasks',
        'partialRetentionScope': 'projection_slot_local'
    }

Такой режим также меняет постановку по сравнению с суточным поиском. Если
расширенные интервалы не покрывают 10:00, путь с первой посадкой в 10:00 не
будет найден. Если покрывают - будет найден, но затем может быть отфильтрован
правилами допустимости.

3.6 Когда число деревьев равно числу районов
--------------------------------------------
В общем случае число деревьев равно числу районов только при условии:
    mode = 'origin_period'
    originScope = 'declared_zones'

Именно originScope = 'declared_zones' означает, что исходные районы поиска
берутся из полного списка районов, а не из спроса.

Если используется:
    mode = 'interval_local'

то число расчетных пакетов определяется активными строками спроса, исходными
районами и временными окнами. Оно не обязано равняться 227.

Если используется:
    originScope = 'active_demand_origins'

то число деревьев равно числу исходных районов, для которых есть положительный
спрос. Оно также не обязано равняться 227.

Таким образом, совпадение числа районов и деревьев выполняется в
общезональном режиме текущего прогона и во всех режимах origin_period с
originScope = 'declared_zones'. Но только режим с
resultProjection = 'completion_targets' дополнительно считает результат по всем
227 * 227 парам районов. Режимы с resultProjection = 'demand_tasks' считают
результат только для строк спроса.

5.3. Постановка выполненного поиска
-----------------------------------
Расчет выполнялся в общезональной постановке:
    исходные районы: все 227 объявленных районов;
    целевые районы: все 227 объявленных районов;
    число пар исходный-целевой район: 227 * 227 = 51 529;
    временной горизонт: полные сутки;
    ограничение пересадок: не более одной пересадки.

Для каждого исходного района строилось одно дерево методом ветвей и границ.
В дереве рассматривались:
    посадки на рейсовые сегменты;
    продолжения по рейсовым сегментам;
    пешеходные подходы к остановкам;
    пешеходные переходы между остановками;
    пешеходные выходы из остановок в целевые районы.

Для пешеходных сегментов применялись правила:
    из исходного района разрешен только подход к остановке;
    после поездки разрешен переход между остановками;
    после поездки разрешен выход в целевой район;
    последовательности пешеходных переходов, не соответствующие этим правилам,
    отбрасываются.

Т.е. поиск строил не произвольные цепочки сегментов, а допустимые
пассажирские пути с учетом порядка "подход - поездка - пересадка - выход".


5.4. Расчет
-----------

Перед поиском были построены вспомогательные индексы для быстрого доступа к:
    возможным посадкам;
    рейсовым продолжениям;
    пешеходным подходам;
    пешеходным пересадкам;
    пешеходным выходам.

Эти индексы не меняют постановку. Они только ускоряют поиск
допустимых продолжений из текущего состояния.

Сам поиск выполнялся параллельно:
    одновременно считалось до 4 деревьев.

Поэтому в логе деревья завершаются не в порядке номеров районов.
Параллельность не меняет множество найденных путей: каждое дерево
соответствует одному исходному району и считается независимо.

Внутри каждого дерева алгоритм последовательно расширял частичные пути и
отбрасывал те ветви, которые уже не могли привести к полезной альтернативе.
Использовались следующие виды отсечения:
    недопустимость по расписанию или структуре пути;
    нарушение правил пешеходных переходов;
    превышение ограничения на пересадки;
    отсутствие достижимости целевого района из текущего состояния;
    доминирование уже найденной более качественной альтернативой;
    невозможность попасть в заданные пороги допустимости по нижней оценке
    оставшейся части пути.

    пешеходные пересадки породили особенно большое ветвление.

Отсечения работали активно. По логу:
    по достижимости и фазовым ограничениям было отброшено более 75 млрд
    проверок на уровне целевых районов;

    по нижним оценкам качества оставшейся части пути было отброшено более
    50 млрд проверок на уровне целевых районов;

    последовательные недопустимые пешеходные расширения отбрасывались более
    35 млрд раз.

Эти числа больше количества сгенерированных продолжений, потому что один
частичный путь проверяется сразу относительно множества возможных целевых
районов.

Наиболее тяжелые деревья имели границу поиска в несколько миллионов частичных
путей. Максимальное зафиксированное значение составило около 7.88 млн частичных
путей на границе поиска. 

5.8. Память
-----------
Наиболее тяжелые деревья требовали значительный объем памяти. По диагностике
одного дерева максимальная нижняя оценка объема основных структур составила:
    около 3.0 ГБ.

Так как расчет выполнялся в 4 потока, несколько тяжелых деревьев могли
находиться в памяти одновременно. Фактическая память процесса должна быть выше
этой оценки, поскольку к основным данным добавляются расходы контейнеров,
таблиц поиска, потоков выполнения и вспомогательных буферов.

Память расходуется прежде всего на границу
поиска, сохранение недоминируемых частичных состояний и удержание завершенных
альтернатив до окончательного отбора.


5.9. Сравнение с ориентиром VISUM около 10 млн путей
----------------------------------------------------

Финальное число для расчета:
    5 799 880

Однако есть два разных счетчика:

11 900 741 - альтернативы после отбора доминирования;
5 799 880 - альтернативы после дополнительного финального отбора по допускам качества.

Если в VISUM под найденными путями понимаются альтернативы после доминирования,
но до финального отбора по допускам качества, то сравнивать следует с числом 11 900 741.

Если же VISUM считает именно финальные альтернативы после тех же правил
допуска, то расхождение 5.8 млн против примерно 10 млн существенно.

Вероятно, место расхождения - единицы измерения абсолютных допусков и
времени ожидания пересадки.

В параметрах заданы:
    minSearchImpAbs    = 10
    minJourneyTimeAbs  = 10
    minTWT             = 1
    maxTWT             = 10

Внутри расчета времена расписания и продолжительности путей хранятся в
секундах. В выполненном прогоне эти параметры были прочитаны без перевода
минут в секунды. Если в исходной постановке VISUM они имеют смысл минут, то
предыдущий прогон применил более строгие условия:
    10 секунд вместо 10 минут для абсолютного допуска по времени пути;
    10 секунд вместо 10 минут для максимального ожидания пересадки;
    1 секунда вместо 1 минуты для минимального ожидания пересадки.

Это способно существенно сократить число допустимых пересадочных
путей и число финально удержанных альтернатив.

После исправления интерпретации входных единиц эти параметры должны
нормализоваться как минуты:
    minSearchImpAbs = 10 минут -> 600 секунд;
    minJourneyTimeAbs = 10 минут -> 600 секунд;
    minTWT = 1 минута -> 60 секунд;
    maxTWT = 10 минут -> 600 секунд.
