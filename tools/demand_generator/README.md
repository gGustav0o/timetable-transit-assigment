# Synthetic Demand Generator

## Назначение

`demand_generator` - консольная утилита для генерации спроса по корреспонденциям между районами.

Она нужна для подготовки двух входных файлов для основного проекта:

- `time_intervals.csv`
- `od_demand.csv`

Утилита использует `connection_segments_input.csv` как источник структуры транспортной сети.

## Что делает утилита

На выходе утилита строит:

1. набор временных интервалов одинаковой длины;
2. суточный спрос для каждой пары районов;
3. разложение суточного спроса по временным интервалам;
4. итоговый CSV в формате, совместимом с моделью проекта.

## Логика работы

### 1. Чтение структуры сети

Утилита читает `connection_segments_input.csv` и извлекает из него:

- множество районов;
- связи район-остановка и остановка-остановка;
- временной диапазон расписания;
- грубые признаки связности сети.


### 2. Построение признаков районов

Для каждого района строится масса района.

Она зависит от того, насколько район представлен в транспортной структуре,
например:

- сколько у него access/egress-связей;
- со сколькими уникальными остановками он связан;
- сколько сегментов заканчиваются или начинаются в этом районе.

Масса района никогда не обнуляется: даже слабо представленный район получает
положительное значение.

Районы должны быть неравноправны. Более крупные или более транспортно проявленные районы должны генерировать больше спроса.

### 3. Построение межрайонной связности

Для каждой пары районов оценивается грубая мера транспортной связанности.

Она выражается через коэффициент `decay(i, j)`, который ослабляет спрос между слабо связанными районами и меньше штрафует хорошо связанные пары.

Спрос должен зависеть не только от самих районов, но и от того, насколько разумно между ними вообще перемещаться в рамках структуры сети.

### 4. Выбор периода моделирования

Утилита выбирает временной диапазон, в котором будет моделироваться спрос.

Возможны два режима:

- явный диапазон через CLI;
- автоматическое определение диапазона по `DEP/ARR` из входного файла.

Спрос строится не на весь день вообще, а на выбранный интервал суток.

### 5. Построение временных интервалов

Выбранный период делится на интервалы одинаковой длины.

Например, при диапазоне `06:00–23:00` и длине интервала `3600` секунд
получается `17` интервалов.

Смысл этого шага: суточный спрос нужно разложить по дискретным временным бакетам.

### 6. Генерация суточного спроса по OD-парам

Для каждой пары районов `(i, j)` строится суточный спрос.

Интуитивно он определяется так:

- чем больше масса района `i`, тем выше его "порождающая" способность;
- чем больше масса района `j`, тем выше его "притягивающая" способность;
- чем хуже связность между `i` и `j`, тем сильнее штраф через `decay(i, j)`;
- добавляется небольшой детерминированный шум.

Шум детерминированный:

- одинаковый `seed` дает одинаковый результат;
- результат не зависит от порядка обхода коллекций;
- для каждой пары `(i, j)` шум строится локально через хэш.

Спрос получается синтетическим, но не равномерным и не симметрично-искусственным.

### 7. Построение временного профиля спроса

После этого для каждой OD-пары строится профиль времени суток.

Он описывает, какая доля суточного спроса приходится на каждый интервал.

Профиль устроен как правдоподобная суточная кривая:

- низкий спрос ранним утром;
- утренний пик;
- дневное плато;
- вечерний пик;
- спад поздно вечером.

Поверх базового профиля добавляется небольшая OD-специфическая детерминированная вариация.

Две пары районов могут иметь похожий, но не идентичный распределенный по времени спрос.

### 8. Разложение суточного спроса по интервалам

Для каждой OD-пары и каждого интервала считается:

`interval_demand = daily_demand * temporal_share`

При этом сохраняется численная согласованность:

- все значения конечны;
- все значения неотрицательны;
- сумма по интервалам равна суточному спросу для данной пары.

Смысл этого шага: итоговая таблица спроса уже готова в формате
`origin_zone_id, destination_zone_id, interval_id, passengers`.

### 9. Фильтрация нулевых и почти нулевых строк

На последнем шаге, непосредственно перед записью CSV, могут быть отброшены
нулевые или слишком малые значения спроса.

Это управляется параметром `sparse_od_threshold`.

Расчетная модель строит полную картину, а output-слой уже решает, какие строки действительно имеет смысл писать в файл.

## Выходные файлы

### 1. `time_intervals.csv`

Формат:

```csv
interval_id,start_sec,end_sec
1,21600,25200
2,25200,28800
...
```

Смысл:

- `interval_id` - идентификатор интервала;
- `start_sec` - начало интервала в секундах от начала суток;
- `end_sec` - конец интервала в секундах от начала суток.

### 2. `od_demand.csv`

Формат:

```csv
origin_zone_id,destination_zone_id,interval_id,passengers
1,2,1,3.5
1,2,2,4.1
...
```

Смысл:

- `origin_zone_id` - район отправления;
- `destination_zone_id` - район назначения;
- `interval_id` - временной интервал;
- `passengers` - спрос на этом интервале.

## Детерминизм

Утилита детерминирована.

Это означает:

- одинаковый входной файл + одинаковый `seed` дают идентичный результат;
- результат не зависит от порядка обхода `dict`/`set`;
- шум задается локально для каждой OD-пары и каждого интервала.

Если поменять `seed`, значения спроса изменятся.

## Как запускать

Запускать утилиту нужно из директории `tools/demand_generator/src`:

```powershell
python -m demand_generator --input ..\..\..\data\test\connection_segments_input.csv --output-dir ..\..\..\data\test\generated_demand --verbose
```

Если запуск идет из другой директории, просто укажи корректные пути к входному
файлу и выходной директории.

## Аргументы CLI

### Обязательные

#### `--input <path>`

Путь к `connection_segments_input.csv`.

#### `--output-dir <path>`

Директория, в которую будут записаны:

- `time_intervals.csv`
- `od_demand.csv`

### Параметры времени

#### `--start-sec <int>`

Начало периода моделирования в секундах от начала суток.

По умолчанию:

```text
21600
```

То есть `06:00:00`.

#### `--end-sec <int>`

Конец периода моделирования в секундах от начала суток.

По умолчанию:

```text
82800
```

То есть `23:00:00`.

#### `--interval-sec <int>`

Длина одного временного интервала в секундах.

По умолчанию:

```text
3600
```

То есть один час.

#### `--auto-time-range`

Если указан, период моделирования будет взят не из `--start-sec/--end-sec`,
а автоматически вычислен по `DEP/ARR` входного файла.

### Параметры генерации спроса

#### `--seed <int>`

Seed детерминированного шума.

По умолчанию:

```text
42
```

#### `--demand-scale <float>`

Глобальный масштаб суточного спроса.

Чем больше значение, тем выше итоговые значения `passengers`.

По умолчанию:

```text
1.0
```

#### `--include-intrazonal`

Если указан, утилита будет генерировать также спрос внутри одного района
(`origin_zone_id = destination_zone_id`).

По умолчанию внутрайонные перемещения не генерируются.

#### `--sparse-od-threshold <float>`

Нижний порог записи спроса.

Если итоговое значение `passengers` не превышает этот порог, строка не будет
записана в `od_demand.csv`.

По умолчанию:

```text
0.0
```

#### `--max-written-od-pairs <int>`

Необязательное ограничение числа OD-пар, записываемых в `od_demand.csv`.

Ограничение применяется после `sparse_od_threshold`. Утилита выбирает пары с
наибольшим суммарным записываемым спросом по всем интервалам; при равенстве
используется детерминированный порядок по `origin_zone_id`,
`destination_zone_id`.

Параметр предназначен для воспроизводимых smoke-прогонов. Он не меняет
синтетическую модель спроса, а только выбирает меньший сценарий для записи.

#### `--max-written-demand-rows <int>`

Необязательное ограничение числа строк, записываемых в `od_demand.csv`.

Ограничение применяется после `sparse_od_threshold` и после
`--max-written-od-pairs`, если он задан. Выбираются строки с наибольшим
значением `passengers`; при равенстве используется детерминированный порядок по
`origin_zone_id`, `destination_zone_id`, `interval_id`.

Этот параметр напрямую ограничивает число demand tasks для расчетного бинарника.

### Диагностика

#### `--verbose`

Печатает подробную диагностическую сводку:

- число входных строк;
- число районов;
- диапазон времени;
- число интервалов;
- число OD-пар;
- суммарный спрос;
- число записанных OD-пар;
- число записанных строк;
- статус прохождения стадий.

## Рекомендуемый первый запуск

Для текущего тестового набора разумно использовать:

```powershell
python -m demand_generator `
  --input ..\..\..\data\test\connection_segments_input.csv `
  --output-dir ..\..\..\data\test\generated_demand `
  --start-sec 21600 `
  --end-sec 82800 `
  --interval-sec 3600 `
  --seed 42 `
  --demand-scale 1.0 `
  --sparse-od-threshold 0.0 `
  --verbose
```

Для быстрого smoke-прогона на крупном тестовом файле лучше явно ограничить
записываемый сценарий, например:

```powershell
python -m demand_generator `
  --input ..\..\..\data\test\connection_segments_input.csv `
  --output-dir ..\..\..\data\test\generated_demand_smoke `
  --start-sec 21600 `
  --end-sec 25200 `
  --interval-sec 3600 `
  --seed 42 `
  --demand-scale 1.0 `
  --sparse-od-threshold 0.0 `
  --max-written-demand-rows 50 `
  --verbose
```

## Пример результата

После успешного запуска в `output-dir` появятся:

- `time_intervals.csv`
- `od_demand.csv`

А в консоли, если включен `--verbose`, будет выведена диагностическая сводка по:

- размеру входа;
- размеру структурной модели;
- временному диапазону;
- числу OD-пар;
- суммарному сгенерированному спросу;
- числу строк, записанных в выходные CSV.

## Практические замечания

1. Утилита не является частью основного C++-бинарника.
2. Она нужна именно как оффлайн-подготовка synthetic input data.
3. Если изменить `demand_scale`, изменится абсолютный уровень спроса, но не
   общая структура генерации.
4. Если изменить `seed`, изменятся локальные вариации спроса, но результат
   останется детерминированным и воспроизводимым.
5. Если включить `--auto-time-range`, число интервалов может измениться.
